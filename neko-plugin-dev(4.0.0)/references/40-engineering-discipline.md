# 40 · 工程纪律：小步、测试、深模块与反过度工程

> 融合来源：
> - **mattpocock/skills**（TDD、代码审查、代码库设计、诊断 bug、小步提交）
> - **DietrichGebert/ponytail**（YAGNI 阶梯、反过度工程、"最好的代码是你没写的代码"）
>
> 这些不是 NEKO 专属的语法，而是写**任何**插件时都应遵守的工程纪律。把它们内化成习惯，能显著减少线上事故与返工。

---

## 1 · 小步提交（Small Steps）

把"我想做个插件"拆成一条条能在 5–15 分钟内完成、且**随时可运行**的小步。每一步都满足：

- 改动后插件仍能 `reload` 不报错；
- 每步有可验证的结果（能跑一次、UI 能渲染、日志有输出）；
- 不跨多步堆叠未验证的代码。

**信号**：如果你发现自己"先一口气写完整个插件再测"，停下来。先把 `@plugin_entry` 的空壳 + 一个 `print`/`report_status` 跑通，再逐步加功能。

**对应 NEKO 实践**：先在 `__init__.py` 里放一个最小可运行插件（仅 `@neko_plugin` + 一个 hello entry），用 `reload` 验证框架能加载，再逐步挂装饰器、加 UI、加定时器。

---

## 2 · 测试驱动开发（TDD）

顺序固定为 **红 → 绿 → 重构**：

1. **红**：先写一个会失败的测试，描述你想要的入口行为（给定输入，期望返回 `Ok` 且 `output` 符合预期，或 `Err` 命中特定错误）。
2. **绿**：写**刚好够用**的实现让测试通过，不要多写。
3. **重构**：在测试保护下清理重复、收敛结构。

**对 NEKO 插件的适配**：

- 纯逻辑（参数解析、配置转换、文本格式化）抽到模块级函数，用 `pytest` 直接测，不依赖框架。
- 依赖 `self.ctx` / `self.db` / `self.store` 的部分，用测试替身（fake）注入，见 `19-llm-workflow-design.md` 与 `05-testing.md`。
- `@llm_tool` 的"契约"优先写测试：给定 `parameters`，断言返回的 `dict` 含 `output` 且 `is_error` 正确。

> 触发条件：当新增分支逻辑、`input_schema` 校验、或 `@llm_tool` 参数转换时，**先写测试**。

## 3 · 代码审查的两轴模型（Code Review）

mattpocock 提出审查只看两个轴：

- **轴 A — 符合标准吗？** 命名、类型、风格是否与代码库一致（类型标注、异步、错误处理模式）。
- **轴 B — 符合规格吗？** 实现是否真的满足了需求，有没有遗漏边界。

做插件时**自我审查**也用两轴：加载 `02-python-plugin.md` 的模板检查签名/装饰器是否规范（轴 A）；再用 `12-master-checklist.md` 逐条核对功能是否齐全（轴 B）。

调试他人/自己的插件时，把审查当作"找证据"而非"挑错"：每一条意见都要能指向具体代码行。

---

## 4 · 诊断 Bug 的循环（Diagnose Bugs）

不要猜。固定循环：

```
观察症状 → 提出假设 → 设计最小实验（加日志/断点/缩窄输入）
        → 运行实验 → 根据证据修正假设 → 复现 → 定位根因 → 修复并加回归测试
```

**NEKO 专属提示**：

- 用 `self.logger` 而非 `print`；日志会进框架日志系统，便于排查（见 `11-undo-and-logging.md`）。
- `AsyncIO` 静默吞异常是头号元凶：入口/`async def` 里未 `await`、未捕获的异常会变成"无响应"。见 `24-error-handling-patterns.md`、`25-concurrency-race-conditions.md`。
- 用 `report_status` 把内部状态暴露到 UI，比反复改代码快得多。

## 5 · 深模块 / 浅模块（Deep vs Shallow Modules）

- **浅模块**：接口很大（很多参数、很多公开方法），实现很薄——调用方要懂一堆细节。
- **深模块**：接口小、实现深，把复杂度藏起来——调用方只说"要什么"，不用管"怎么做"。

**插件设计应用**：

- 把"怎么调外部 API / 怎么拼 prompt / 怎么存库"封装进**少数深函数**，entry 只负责"取参数 → 调深函数 → 返回 `Ok`/`Err`"。
- `@llm_tool` 的参数表面要窄：只暴露用户真正要填的字段，内部复杂度（重试、限流、格式转换）藏起来。
- 不要为了"显得灵活"把内部开关全做成配置项——那是把复杂度甩给调用方。

## 6 · YAGNI 阶梯（ponytail）：反过度工程

ponytail 的核心：**最好的代码是你没写的代码**。每当想加东西，沿阶梯从下往上问，能停在低层就别往上爬。下面是 ponytail 的**真实阶梯**（9 级，0 在最底）：

```
(0) 什么都不做        —— 真的需要这个功能吗？删掉它比实现它更有价值。
(1) 改文案/复制粘贴    —— 写死一次是否就够？
(2) 抽函数            —— 仅当同一段逻辑出现 ≥2 次。
(3) 加参数/配置        —— 让已有函数覆盖新情况，别另写一套。
(4) 抽类/模块          —— 状态或行为确实成体系时才做。
(5) 抽象基类/接口/泛型 —— 仅在 ≥3 个真正不同的实现需要统一契约时。
(6) 插件化/依赖注入/运行时动态加载 —— 仅在必须支持第三方扩展时（NEKO 自身的插件机制才用得到）。
(7) 自研 DSL / 代码生成 / 元编程 —— 几乎永远不要。
(8) 分布式/跨进程/多节点 —— 除非你真的在做一个分布式系统，否则别碰。
```

### ponytail 的 7 条具体规则（原文要义）

1. **先复制，后抽象**。同样代码出现第 1 次：直接写；第 2 次：再复制一次也行；第 3 次：才考虑抽。不要在第 1 次就"预见性抽象"。
2. **没有 ≥3 个真实不同的实现，就不该有抽象基类 / 接口 / 泛型**。两个相似函数用参数区分就够了，别建层级。
3. **配置项不是免费的**。每多一个设置项，就多一份 UI、一份文档、一份用户困惑。只暴露用户**会改**的项。
4. **不要造框架**。你的插件不需要"插件系统""钩子总线""规则引擎"——NEKO 已经提供了 `@hook`、动态 entry、Bus（`32-nekopluginbase-internals.md`、`31-bus-system-internals.md`）。用框架的。
5. **重试 / 限流 / 超时 / 熔断这些"基础设施"只有在你真的被它坑过才加**。不要预设网络会挂而提前写一整套 resilience 层；先 `try/except → Err`（`44-local-plugin-architecture.md` §6），真遇到再补。
6. **数据库抽象层（自建 ORM / Repository 模式）几乎总是过度**。能用 `self.store` / `self.config` + 简单查询解决的，绝不引入额外持久化层（`38-config-system-internals.md`）。
7. **"以后可能要扩展"不是现在写的理由**。YAGNI = You Aren't Gonna Need It。等需求真的来，再重构也不迟，而且那时你才知道它到底长什么样。

### NEKO 插件实战对照（逆向验证）

- **不要在插件里造"插件系统"**：`galgame_plugin` 虽有 40 个 `_Galgame*Mixin`（`44-local-plugin-architecture.md` §1 范式 B），但那是"能力聚合"不是"动态加载子插件"——它没有自研钩子总线，全部用框架的 `@plugin_entry` / `@ui.action`。这是**对的**用法；错的是去写 `load_plugin(path)` 之类的自研机制。
- **配置项用 `SettingsField(hot=True)`**：真实插件（`lifekit/__init__.py:54-67`）只把用户会改的字段标 `hot=True`，自动出面板，不手写 `[[plugin.ui.action]]`。印证规则 3。
- **持久化用 `self.config` / `self.store`**：逆向中**没有**任何插件自建 ORM（`44-local-plugin-architecture.md` §0）。印证规则 6。
- **"为了好看"的抽象是 AI 高发区**：泛型基类、工厂、策略模式常出现在"还没写功能先写架构"的草稿里。先用最直接的写法（`02-python-plugin.md` 模板）跑通，确认重复了再抽。

**一句话规则**：每当你准备写第 6–8 级抽象时，先问"能不能降到第 1–2 级？" 多数时候能。

## 7 · 把它们串起来：一个插件的最小健康循环

1. 用"小步"把最小可运行插件跑起来（仅装饰器壳）。
2. 对核心逻辑先用 TDD 写红测试，再写绿实现。
3. 把复杂度收进"深模块"，entry 保持薄。
4. 每加一处功能，先用 YAGNI 阶梯确认它该在第几级——能不写就不写。
5. 用"两轴审查"自查：规范（轴 A）+ 功能（轴 B）。
6. 出问题走"诊断循环"，用日志与 `report_status` 取证，修完补回归测试。
