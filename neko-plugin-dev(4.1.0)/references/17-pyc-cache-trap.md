# 17. `__pycache__` 缓存陷阱 — 代码改了但不生效

> 基于 `ai_singer` 插件开发中最费时的调试经历：改了代码、没有任何报错，但运行的是旧逻辑。
>
> 本文已对照官方开发流程（Reload / Load unpacked）核对。**清缓存是"行为不更新"的兜底诊断分支，不是常规必做动作**；日常优先用官方 Reload 生效。

---

## 17.1 问题现象

```
你修改了 __init__.py → 重启/重载 → 日志仍显示旧代码在运行
→ 旧 entries 仍然存在
→ 旧配置项仍然被持久化
→ 旧日志仍然在输出
```

**关键特征**：没有报错、没有异常、没有崩溃——只是行为不变。这比报错更难排查。

---

## 17.2 需要先排除的三个更常见原因

在怀疑 PY 字节码缓存之前，先依次排除（**顺序很重要**）：

1. **改动根本没到运行位置**：源码树/开发者模式下需点 **Reload**；手工同步场景确认源文件已真正覆盖。
2. **插件进程没有真正重载**：只改了依赖或 `plugin.toml` 时，需要**重启该插件**而非仅 Reload；改了 Python 源码则 Reload 即可。
3. **有多个副本/多个进程**：工作区、已安装副本、内存中已导入的模块对象是三层，任何一层旧都会表现为"改了没生效"。

以上都正常仍不更新，才看字节码缓存。

---

## 17.3 字节码缓存是怎么误导人的

Python 首次 `import` 会把 `.py` 编译为 `.pyc`，放在 `__pycache__/`：

```
ai_singer/
├── __init__.py                          # ← 你修改了这个
├── __pycache__/
│   └── __init__.cpython-313.pyc         # ← 校验通过时会被直接加载
```

Python 会在 `.pyc` 头部记录**源文件的 mtime 与大小**，导入时与当前 `.py` 比对：

- 一致 → 直接用 `.pyc`
- 不一致 → 重新编译并刷新 `.pyc`

真正容易踩的坑是**文件复制**：

- 把工作区的 `__pycache__` **连同源文件**一起复制到运行目录，复制工具**保留时间戳**，于是目标端 `.pyc` 头部记录的源 mtime 与目标端 `.py` 的 mtime 恰好一致 → 校验通过 → 继续用旧字节码。
- 反之，只要源 `.py` 的 mtime/大小变化，Python 通常会正确重编译。所以"删缓存是唯一可靠方法"的说法**不成立**——它只是当校验被复制行为欺骗时的兜底手段。

---

## 17.4 哪些操作会/不会触发残留

| 操作 | 是否清除缓存 | 说明 |
|------|:---:|------|
| 修改 `.py` 文件（mtime/大小变化） | ⚠️ 视情况 | 一般会使缓存失效；被复制的时间戳欺骗时不会 |
| 官方开发模式点 **Reload** | ⚠️ 视情况 | 重新加载模块，但**不保证**清字节码缓存 |
| 从工作区**连同 `__pycache__` 一起**复制 | ❌ | 缓存被带过去（最常见的坑） |
| 重启 N.E.K.O | ❌ | 重启不清磁盘缓存 |
| 手动删除目标 `__pycache__/` | ✅ | 兜底手段（先确认前两节原因已排除） |
| `python -B` 运行 | ✅ | 禁用字节码写入（不适用 N.E.K.O） |

---

## 17.5 处理方式

### 首选：用官方方式让改动生效

- 源码树 / 开发者模式：**Reload**；改了依赖或 `plugin.toml` 后**重启该插件**。
- 已安装包：重新 `build` 并导入 `.neko-plugin`。

### 兜底：清理目标缓存（仅在上一步无效时）

```powershell
# Windows PowerShell
Remove-Item -Path "path\to\plugin\__pycache__" -Recurse -Force
```

```bash
# Linux / macOS
rm -rf path/to/plugin/__pycache__/
```

### 若确实需要脚本同步（已安装包场景的兜底）

**不要用 `robocopy /MIR`**：`/MIR` 会删除目标端多余文件，源路径手误可能清空数据。要镜像先 `/L` 预览：

```powershell
$src = "E:\workspace\my_plugin"
$dst = "$env:LOCALAPPDATA\N.E.K.O\plugins\my_plugin"

# 仅同步源文件并排除缓存；先 /L 预览确认删除清单
robocopy $src $dst /MIR /XD __pycache__ node_modules .git /L

# 预览无误后去掉 /L 执行；再清一次目标缓存作为诊断
robocopy $src $dst /MIR /XD __pycache__ node_modules .git
if (Test-Path "$dst\__pycache__") { Remove-Item "$dst\__pycache__" -Recurse -Force }
```

---

## 17.6 如何确认代码已生效

以启动日志为证据，任选其一对比"改前 / 改后"：

| 观察点 | 日志关键字 |
|--------|-----------|
| 入口集合 | `Plugin entries collected:`（删除的 entry 应消失） |
| 持久化配置 | `配置已持久化:`（只应出现新配置项） |
| 依赖校验 | `config schema validation warnings:`（消失的依赖不应再警告） |
| 启动完成 | `启动完成`（附加字段应随之变化） |

---

## 17.7 为什么这类问题在 N.E.K.O 插件里特别烦

1. **独立进程**：插件在子进程中运行，IDE 的 "Restart Kernel" 之类清不掉它的模块状态。
2. **多副本**：工作区 / 运行位置 / 内存对象三层，任何一层旧都表现为不生效。
3. **无显式报错**：语法没问题，只是版本不对。
4. **时间戳被复制保留**：让 `.pyc` 校验"看起来"仍然有效。

---

## 17.8 预防

- 在插件目录放 `.gitignore`：

```gitignore
__pycache__/
*.pyc
*.pyo
```

- 同步时排除 `__pycache__/`、`*.pyc`（示例见 §17.5）。
- 交付走 `neko-plugin build`，不要手工连缓存一起复制。

> 对应铁律 #7：**优先用官方开发模式 Reload**；仅在手改源码/已安装包或行为不更新时，才删目标 `__pycache__/` 作为诊断分支。

---

## 17.9 速查

| 症状 | 先查 | 再查 |
|------|------|------|
| 删除的 entry 仍在日志 | 是否 Reload / 是否覆盖了文件 | 目标 `__pycache__/` |
| 删除的配置项仍被持久化 | `plugin.toml` 是否同步 / 插件是否重启 | 目标 `__pycache__/` |
| 删除的依赖仍报警告 | 依赖声明是否更新 | 目标 `__pycache__/` |
| 新增的 entry 不出现 | 文件是否到运行位置 | 目标 `__pycache__/` |
| 新增的配置项不生效 | `plugin.toml` 是否同步 | 目标 `__pycache__/` |
